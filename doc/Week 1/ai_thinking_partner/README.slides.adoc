== Introduction

* AI as a collaborative tool
* Ownership of cloud architecture and operational decisions
* Example: Event-driven cloud pipeline

== Key Concept: AI as Draft

* AI output = proposed artifact
* Must be checked before use
* Risk of false confidence
* Need for verification workflow

== Productive AI Use

* Comparing cloud services and architecture options
* Asking for alternatives and critiques
* Avoiding AI as an answer machine
* Prompts should focus on cost, reliability, security, and validation

== AI Failure Modes

* Incorrect, incomplete, or misleading outputs
* Need to deliberate on predictable failures
* Examples: invented APIs, stale service limits, and hidden infrastructure assumptions

== Distributed-Systems Blind Spots

* AI often assumes reliable networks and sequential execution
* Cloud workloads overlap, retry, scale, and fail independently
* Issues: duplicate events, partial failures, stale state, and cascading failure
* Review boundaries, shared state, retries, timeouts, and idempotency

== Individual Integrity Packet

* Record of AI usage and corrections
* Distinguishes learning from outsourcing
* Contents: prompts, critiques, evidence
* Must be visible and connected to design

== Worked Example

* Problem: Process an event in a cloud pipeline
* Naive implementation may pass a local test
* Hidden assumptions: exactly-once delivery and no worker failures

== Failure Scenario

* A broker redelivers an event after a worker timeout
* Two workers process the same event and duplicate a side effect
* The proposed design omitted idempotency and retry behavior

== Safer Design Direction

* A design that ties side effects to state transitions
* Only the operation that wins the transition emits effects

```python
def process_event(event):
    if claim_idempotency_key(event.id):
        result = transform(event.payload)
        store_result_once(event.id, result)
        acknowledge(event)
```

== Integrity Packet Entry

* AI Output Summary: Simple event consumer with no failure handling
* Critique: Did not discuss retries, duplicate delivery, or partial failure
* Evidence: Redelivery test produced duplicate output
* Revision: Add an idempotency key and explicit acknowledgement behavior
* Validation: Verified one durable result across repeated delivery

== Failure Modes and Anti-Patterns

* AI produces code that compiles but violates invariants
* Invented APIs or citations
* Omissions of failure behavior
* Student inability to explain AI output
* Logged suggestions without critique

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use

| AI for brainstorming
| Expands options quickly
| Generic alternatives
| Early design exploration

| AI for code draft
| Speeds implementation
| Misses constraints
| Reviewed code units

| AI for test ideas
| Surfaces edge cases
| May lack relevance
| Validation planning

| AI for critique
| Challenges assumptions
| Misses domain-specific failures
| After baseline design

| No AI use
| Forces independent thought
| Reduces design exposure
| When unaided work is needed
|===
